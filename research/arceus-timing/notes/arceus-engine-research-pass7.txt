2. AI NAVIGATION STEPS 1/30 PER RENDERED FRAME (MEASURED)
Timing-research probe on 2795204 (hkaiWorld::stepWorld path), same run:
navigation and main physics calls have identical counts (6900 each by 98 s), both from
caller 2968538, i.e. once per rendered frame. variable_mode (+150) stayed 0 for the whole
run, so the fixed 1/30 step was selected every frame while the elapsed input was
0.008-0.016 s. At about 66 FPS AI navigation therefore advances about 2.2x real time.
This is the same defect as the main physics world before SNX_ARCEUS_PHYSICS_TIMESTEP_FIX.
Not yet corrected. Note: the FCSEL is at 2795204+0x40 but, unlike the physics wrapper,
this path has no zero-step gate, so a min(1/30, elapsed) rewrite must also handle a zero
or tiny elapsed input before it is safe. Visible effect (wild Pokemon and NPC path
following, steering) still to be confirmed in gameplay.

3. CADENCE CENSUS (BUILT, NOT YET RUN)
Purpose: the pass-1 audit lists 58 fixed-step sites but could not establish whether each
owner runs once per rendered frame (a high-FPS bug) or on a 30 Hz schedule (fine).
SNX_ARCEUS_CADENCE_CENSUS=1 (requires SNX_ARCEUS_TIMING_RESEARCH=1) wraps 32 owner
functions with one read-only counting wrapper. Each uses the existing equivalent
B -> CBZ XZR rewrite at an in-function branch, with head-word and branch-word guards and
an exact function-length match. Owners already wrapped by other fixes are excluded
(capture sequence 180C338, transform timers 1D482B0/1D49144, blink, camera, water,
navigation, physics, ball flight).
Every 5 s it logs "arceus-cadence:" lines: frames_per_s (main-world physics calls) and, per
owner, calls_per_s plus object_calls_per_s for one sampled x0 object. Reading the result:
  object rate ~ frames_per_s  -> per-frame owner: its fixed step is a real high-FPS bug
  object rate ~ 30            -> scheduled at 30 Hz: no correction needed
  totals large, object small  -> many objects; use the object rate
x0 is not always an object (helpers), so treat helper rows with care.
